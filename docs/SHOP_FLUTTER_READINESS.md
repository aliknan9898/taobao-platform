# تجهيز kinan Shop لتطبيق Flutter

النطاق هو تطبيق عميل واحد لأجهزة Android وiOS. تستمر واجهات Seller وAdmin وWarehouse عبر الويب، مع ربطها بعقود الطلبات والمخزون والشحن في الخادم الحالي.

| المرحلة | العقد أو المتطلب | دليل القبول |
|---|---|---|
| التصفح | إعدادات السوق عبر `/api/config/public`، ثم الكتالوج حسب بلد التوصيل | البلد اليدوي يعمل عند رفض إذن الموقع. المنتج غير المؤهل لا يظهر ولا يمكن دفعه من سلة قديمة |
| الدفع | `/api/shipping/quote` ثم `/api/buyer/checkout` | مفتاح `Idempotency-Key` ثابت طوال محاولة الطلب نفسها ويُغيّر عند تغيير بياناتها. تأكيد الدفع من الخادم بعد التحقق من إشعار Stripe |
| العمليات | عقد الطلب المشترك وتقارير الحالة بين Shop وSeller وAdmin وWarehouse | طلب تجريبي كامل من الدفع حتى التسليم. Seller يرى طلباته فقط، وWarehouse يرى البيانات اللازمة للتجهيز، والصلاحيات المالية تُفرض في الخادم |
| الحساب | `GET/POST /api/buyer/account/delete` و`/delete-account` | إضافة المسار إلى إعدادات تطبيق Flutter واختبار تسجيل الدخول والتأكيد والحساب الموقوف بسبب طلب مفتوح |
| الإشعارات | مسار الأجهزة الحالي يتوقع Expo. يحتاج تطبيق Flutter تكامل FCM وAPNs وتحديث الرموز وإلغاء التسجيل عند الخروج | اختبار إشعار الشحن والتسليم وفشل التسليم على أجهزة فعلية، ورابط يفتح الطلب الصحيح وفق صلاحية المستخدم |
| المتاجر | إعداد بناء مستقل للاختبار والإصدار، سياسة الخصوصية، إفصاحات البيانات، وحساب مراجعة تجريبي | بناء Android وiOS موقع، اختبار Play وTestFlight، وموافقة قبل إرسال الإصدار |

ابدأ بعقود API واختبارات مرحلة التشغيل، ثم ثبّت معرّفات التطبيق والتوقيع ونسخ بيئات البناء. أبقِ بيانات الموردين والدفع تجريبية في اختبارات التكامل. حماية إعادة المحاولة في هذا الفرع تشارك التنفيذ بين الطلبات داخل عملية خادم واحدة. قبل تشغيل عدة عمليات تؤدي checkout بالتوازي، أضف قيدًا ذريًا في قاعدة البيانات لمنع تكرار الطلب عبر العمليات.
